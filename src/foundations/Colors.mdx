# Colors

Every color in the system is a CSS custom property declared in
`src/tokens.css`, with a counterpart under the `.dark` class. There is no
separate dark palette file and no JS theme object — one stylesheet holds
both modes.

**Read them with `var()`** — `background: var(--color-surface-raised)`,
`color: var(--color-text-subtlest)`, `border-color: var(--color-border)`. Because
the variable changes rather than the rule, a component written this way
switches theme without a single conditional: there is no light branch and
no dark branch anywhere in the kit's CSS.

**The swatches below read their values out of the live document**, so a
color shown here is the value the components actually get. The token
*names* are still listed by hand in `Colors.stories.tsx`, though — add a
token to `tokens.css` and it will not appear here until it is added there
too.

## Surfaces

`--color-surface` is the page. `--color-surface-raised` and `--color-surface-overlay` are surfaces that sit
a level above it — a card inset in the page, a menu floating over it. In
light mode the page is gray-50, a cool off-white, and card/popover are
white: a panel separates from the page by being lighter, so it needs a
border at most, not a shadow. In dark mode `--color-surface` sits at the
darkest step and card/popover are lifted one step toward the viewer.

Each surface has a `-foreground` partner, and the pair is the contract:
put `--color-text` on `--color-surface-raised`, never `--color-text`, even where the
two happen to be equal today.

## Subtle surfaces

`--color-background-neutral` and `--color-background-neutral` are the same value in both modes and differ only
in intent. `--color-background-neutral` is for surfaces that recede — a disabled field's
fill, a table's zebra stripe — and is the only one of the two with a
foreground meant for *long-form* secondary text. `--color-background-neutral` is for
surfaces that are reacting to the user: hover on a menu item, the
selected row in a list.

They are interchangeable in appearance, so nothing breaks visually if you
swap them, and nothing tells you that you did. The distinction is the
whole point: when a brand color eventually replaces one of them, only the
intent that should change will change.

## Solid actions

Filled controls. `--color-background-brand-bold` is the default button and **the brand hue** —
blue out of the box, and the one token the
[`accentColor`](?path=/docs/foundations-overview--docs) setting moves. It
lightens in dark mode rather than darkening, so `--color-text-brand-inverse`
inverts with it.

`--color-background-danger-bold` is a hue too, but a fixed one: it stays red whatever the
accent is. A status colour that follows the brand stops being a status —
if the accent is already red, distinguish destructive actions by wording
and placement, not by colour alone.

A note on names: the token called `--color-background-neutral` is **not** the brand hue. It
is a subtle surface (hover, selected row). The brand hue is `--color-background-brand-bold`.
The collision is unfortunate and predates this kit — the names come from
the token contract the registry is compatible with.

## Lines and focus

`--color-border` is a divider or a container edge, `--color-border` is a form control's
edge, `--color-border-focused` is the focus indicator. None of them take a foreground —
they are only ever an outline color, never a fill behind text.

`--color-border` and `--color-border` are the same value in both modes and, like
muted/accent, are separated by intent rather than appearance. In dark mode
they stop being opaque neutrals and become white at 10% and 15% alpha
respectively, so an edge reads consistently whether it sits on
`--color-surface` or on a lifted `--color-surface-raised`. That is the one place the palette
uses transparency.

## Dark mode

Every token on this page has a counterpart under `.dark`, switched by a
class rather than a media query, and dark is not a mechanical inversion of
light — surfaces go *up* rather than down, and strong fills get lighter so
their foregrounds flip to dark text. The Light/Dark columns in the
contrast table below cover both.

The mechanism, the three places an inversion would have gone wrong, and
how to follow the OS setting are on their own page:
**[Dark mode](?path=/docs/foundations-dark-mode--docs)**.

## Contrast

Measured, not assumed — every pair below is computed from the OKLCH
values in `tokens.css`. WCAG AA wants 4.5:1 for body text and 3:1 for UI
component boundaries such as a focus ring.

| Pair | Light | Dark |
| --- | --- | --- |
| `background` / `foreground` | 19.28:1 | 19.28:1 |
| `card` / `card-foreground` | 20.13:1 | 17.00:1 |
| `popover` / `popover-foreground` | 20.13:1 | 17.00:1 |
| `primary` / `primary-foreground` | 5.03:1 | 6.79:1 |
| `secondary` / `secondary-foreground` | 16.13:1 | 14.07:1 |
| `accent` / `accent-foreground` | 16.13:1 | 14.07:1 |
| `destructive` / `destructive-foreground` | 4.56:1 | 6.19:1 |
| `muted` / `muted-foreground` | 4.60:1 | 5.64:1 |
| `background` / `muted-foreground` | 4.85:1 | 7.73:1 |
| `background` / `ring` | 6.54:1 | 7.63:1 |

Measured on the defaults: blue accent, gray gray. The `primary` row is the default blue accent. Every one of the seventeen
accents is measured the same way and clears 4.5:1 for its own label — see
[Overview → Accent color](?path=/docs/foundations-overview--docs).

**`--color-text-subtlest` on `--color-background-neutral` is 4.60:1 in light mode**, the
tightest pair it forms. It used to be 4.34:1, under AA: gray-500 on every
ramp has since been darkened to the lightest value that clears 4.6:1 on
its own gray-100, so muted text can now sit on a muted fill. On the page background, where secondary
text usually lives, the same token is 4.85:1.

**`--color-text-subtle` is a step between body text and muted text**
(gray-600 light, gray-300 dark): navigation labels that should recede
until hovered or current, as in the Claude apps' sidebar. It reads about
7.5:1 on the light page, so it is body-safe; use `--color-text-subtlest` for
genuinely secondary text.

**`--color-background-input` is a filled panel that muted text can sit on.**
Muted text reads 4.85:1 on it (gray-50) and 5.64:1 on gray-800 in dark — a step off `--color-surface-raised` so a filled panel still reads as filled. The build
measures `--color-text-subtlest` on `--color-surface`, `--color-surface-raised`,
`--color-background-input` and `--color-background-neutral` in both modes on all nine gray ramps, and
stops if any pair drops under 4.5:1. The tightest is neutral on `--color-background-neutral`,
at 4.60:1.

**`--color-border-bold` outlines a checkbox, radio or switch track.** Those
controls have nothing else that shows they are there, so WCAG 1.4.11 wants
3:1 against the page — and `--color-border` (gray-200) is about 1.3:1. The build
measures it on all nine gray ramps.

**`--color-border-input` is the text-field edge** (gray-300 light, white 18%
dark), about 1.5:1: the light hairline of the Claude apps, and a
deliberate exception to 3:1 for fields only. Fields lean on a white
`--color-surface-raised` fill, a faint drop, the label and the focus ring instead. A
product that needs 3:1 sets `--color-border-input: var(--color-border-bold)`.

**`--color-text-brand` is the brand hue as text** — an outlined or ghost
primary button. The solid is picked for its label, not for being read on
the page, and amber-500 on white is barely 2:1, so the build measures a
third step per accent that clears 4.5:1 against the page.

**Two values are deliberately off the beaten path.** `--color-border-focused` follows the
accent at its `-700` step rather than being a neutral, because a focus
indicator has to clear 3:1 against the page under WCAG 1.4.11 and the
lighter solids miss it — yellow-600 measures 2.93:1, so the ring uses a
step darker than the fill for every accent.
And dark `--color-text-danger-inverse` is neutral-900 rather than near-white:
dark mode inverts the destructive fill to red-400, and near-white on
red-400 is 2.77:1, which makes the label of a destructive button in dark
mode fail AA outright.

## Status

Four fixed hues for messages about state: `info` (blue), `success`
(green), `warning` (amber), `danger` (red). Like `--color-background-danger-bold`, they do
not follow the accent. Each comes as four tokens:

| Token | Use | Light | Dark |
| --- | --- | --- | --- |
| `--{status}` | Solid fill | 600 (green 700, amber 500) | 400 |
| `--{status}-foreground` | Label on the solid | neutral-50 (amber: neutral-900) | neutral-900 |
| `--{status}-subtle` | Tinted fill | 100 | 950 |
| `--{status}-text` | Text, icon and border on the tint or the page | 800 | 300 |

The steps are pinned by hand, so `npm run tokens` measures them and fails
the build if any pair drops under 4.5:1:

| Pair | info | success | warning | danger |
| --- | --- | --- | --- | --- |
| label on solid, light | 5.03:1 | 4.73:1 | 8.35:1 | 4.56:1 |
| text on subtle, light | 7.25:1 | 6.45:1 | 6.41:1 | 6.86:1 |
| text on page, light | 8.84:1 | 7.09:1 | 7.13:1 | 8.37:1 |
| label on solid, dark | 6.79:1 | 10.09:1 | 10.43:1 | 6.19:1 |
| text on subtle, dark | 8.13:1 | 10.67:1 | 10.37:1 | 8.40:1 |
| text on page, dark | 10.93:1 | 14.16:1 | 13.69:1 | 10.30:1 |

`danger` and `destructive` share red-600 but mean different things:
`destructive` is an action that destroys, `danger` is a state that is
wrong. Keep them apart so either can move without the other.

## Color is never the only signal

`--color-background-danger-bold` on a button does not say what will be destroyed, and a red
badge means nothing to a reader who cannot distinguish it from a neutral
one. Pair color with words, an icon, or a shape every time it carries
meaning. The contrast numbers above are a floor, not a design review.

## Where the values come from

**Every value is a step off a published ramp, digit for digit.** Nothing
here was hand-picked or eyeballed. Two ramps feed the palette and each is
swappable on its own: an **accent** (blue by default) for `--color-background-brand-bold` and
`--color-border-focused`, and a **gray** (the `gray` ramp by default) for everything structural.

| Token | Light | Dark | Driven by |
| --- | --- | --- | --- |
| `background` | gray-50 | gray-950 | gray |
| `foreground` | gray-950 | gray-50 | gray |
| `card`, `popover` | white | gray-900 | gray |
| `card-foreground`, `popover-foreground` | gray-950 | gray-50 | gray |
| `primary` | accent-600 | accent-400 | **accent** |
| `primary-foreground` | white or near-black | near-black | **accent** |
| `secondary`, `muted`, `accent` | gray-100 | gray-800 | gray |
| `secondary-foreground`, `accent-foreground` | gray-900 | gray-50 | gray |
| `selected` | gray-200 | white 10% | gray |
| `hover-overlay` | black 5% | white 6% | fixed |
| `scrim` | black 50% | black 50% | fixed |
| `muted-foreground` | gray-500 | gray-400 | gray |
| `subtle-foreground` | gray-600 | gray-300 | gray |
| `surface-filled` | gray-50 | gray-800 | gray |
| `neutral-solid` | gray-600 | gray-600 | gray |
| `neutral-solid-foreground` | gray-50 | gray-50 | gray |
| `destructive` | red-600 | red-400 | fixed |
| `destructive-foreground` | neutral-50 | neutral-900 | fixed |
| `border`, `input` | gray-200 | white 10% / 15% | gray |
| `field-border` | gray-300 | white 18% | gray |
| `control-border` | gray-500 | gray-400 | gray |
| `ring` | accent-700 | accent-400 | **accent** |
| `primary-text` | first of accent-600…900 at 4.5:1 on the light page | first of accent-400…200 at 4.5:1 on the dark page | **accent** |

The light accent step is `-600` for most hues but `-700` for sky, fuchsia,
pink and rose, and the label is white or near-black depending on which one
clears 4.5:1 on that fill — the warm hues take dark labels. Exceptions to
the ramp rule: light `--color-surface-raised`/`--color-surface-overlay` (pure white, so a panel reads
lighter than the gray-50 page) and dark `--color-border`/`--color-border`/`--color-background-selected`, and `--color-interaction-hovered` in both
(alpha, so they work over any surface — the sidebar's hover sits on
`--color-background-input`, which in dark equals the opaque `--color-background-neutral` fill).

`--color-background-danger-bold` deliberately does **not** follow the accent. A status
colour that changes with the brand stops being a status.

## Naming

Token names describe a **role**, not a property or a color. `--color-background-brand-bold` is
not "the brand color" and `--color-background-danger-bold` is not "red"; they are the
default action and the dangerous one. The names are also the common
contract most token-based kits share, which is what lets a component
copied out of Zweihänder resolve against tokens a target project already
has instead of arriving with its own private palette.

Figma, by contrast, conventionally names tokens by property —
`bg/primary`, `text/primary`, `border/default`. Those do not map one to
one: Figma's `text/primary` is this system's `--color-text`, and its
`bg/primary` is `--color-surface`. Neither is `--color-background-brand-bold`. Worth pinning down
before any Figma sync, since the collision is silent.

## Primitives

The full underlying palette — 22 hues × 11 shades. None of these
classes are referenced anywhere in the kit, so they are force-generated by
an `@source inline(...)` directive in `src/index.css` purely so this page
can render them.

This is raw material, not a palette to build UI from. Reach for a
primitive when you are defining the *next* semantic token; if a primitive
shows up in a component, a token is missing.

## Customization

Swap the raw values in `:root` and `.dark` in `src/tokens.css`. Nothing
that reads `var(--color-background-brand-bold)` or `var(--color-text-subtlest)` changes, because
every rule points at the variable rather than the value.

Two things to carry through a rebrand: re-measure the pairs in the
contrast table — a brand hue at the same *lightness* as neutral-900 will
not necessarily hit the same ratios — and keep light and dark as separate
decisions. Lifting a brand color for dark mode by reusing the light value
is what produces the 2.77:1 failure documented above.

Projects that install through the registry get these values merged into
their own stylesheet; projects on the npm package import
`zweihander/tokens.css` and override afterwards.
