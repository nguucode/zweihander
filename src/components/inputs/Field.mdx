# Field

<DocTabs>
<DocTab value="overview">

The label, required mark, info note and helper text for a control
that has none of its own.

<Status of={FieldStories} />

Every Zweihänder control (Text Input, Select, Checkbox and the rest)
already carries this anatomy. Field is for the control that does not: a
native element the kit has no component for, a Base UI primitive, or one
of your own. It wires the label, description and invalid state to it
through Base UI Field.

<Canvas of={FieldStories.Default} />

## Variants

There is one appearance. What changes is which optional parts are there.

<Canvas of={FieldStories.Validation} />

| Part | Use for |
| --- | --- |
| `helperText` | The format, limits or purpose, in a line; the error message when invalid. |
| `labelInfo` | A longer rule or explanation most people do not need every time: behind an info button, so the form stays short. |
| `validationState` | `error` when the value cannot be accepted: the helper text says what to change, and it and the edge turn red. `success` for a value checked and accepted. |
| `required` | An asterisk after the label. |

- **Hover** and **focus** belong to the control. The info button turns
  `--foreground` on hover and draws the `--ring` outline on keyboard focus.
- **Error** colours the helper text, which then says what to change, and
  the edge of a field box inside.
- **Read-only** is set on the control (`readOnly`), not on the Field.
  A field box with a read-only control inside is filled with
  `--surface-filled`; the edge, label and helper stay as they are.
- **Disabled** disables the control; how it dims is the control's own. The
  info button stays active: the note may say why the field is disabled.

## API

<div style={{ overflowX: 'auto' }}>
  <ArgTypes of={FieldStories} />
</div>

`FieldControl` is Base UI's `Field.Control`: an `<input>` by default, any
element through `render`, with the label, description and invalid state
wired to it. A Base UI control (Slider, Number Field, Checkbox) inside a
Field wires itself.

### Differences from the spec

- **No separate error part.** As in every Zweihänder control, the error
  is the helper text in the error state (the kit's API convention), so a
  field never shows a hint and an error at once.
- **The info note is a toggletip**, opened by press or Enter, not a
  hover tooltip: tooltips do not open on touch.

## When to use

Use a Field round a control that has no label of its own. Keep the helper
text to a line; put a longer rule behind `labelInfo`.

<DoDont
  do={<Story of={FieldStories.DoLongNoteInInfo} />}
  doCaption="The format in a line under the control; the full rule behind the info button."
  dont={<Story of={FieldStories.DontLongHelper} />}
  dontCaption="A paragraph of helper text pushes every field below it down, on every visit."
/>

An **error** says what to change, not only that something is wrong.

<DoDont
  do={<Story of={FieldStories.DoSayWhatToFix} />}
  doCaption="The error names the allowed range."
  dont={<Story of={FieldStories.DontVagueError} />}
  dontCaption="'Invalid value' leaves people guessing what to change."
/>

### Read-only

A value people need to see but cannot change here (set by a rule,
another team or their role) stays a field: put `readOnly` on the control
and say in `helperText` why, and who can change it. Every Zweihänder
control takes `readOnly`. The boxed fields (Text Input, Textarea,
Search, Number Input, Select, Combobox, Date Picker, Date Range Picker)
all look the same: a filled box, still focusable, the value selectable
and submitted with the form. Checkbox, Radio, Switch and Rating keep
their look, since their mark is the value, and only stop changing.

<DoDont
  do={<Story of={FieldStories.DoReadOnlyWithReason} />}
  doCaption="Read-only: readable, focusable, copyable, and it says who can change it."
  dont={<Story of={FieldStories.DontDisableToLock} />}
  dontCaption="Disabled: dimmed below readable contrast, skipped by Tab, not submitted."
/>

- **Not disabled.** A locked value is still read and copied; a disabled
  one is not (Disabled, below, is for "not yet").
- **No lock icon by default.** The fill already marks the state, and an
  icon would need its own name for screen readers; the helper text says
  more than a lock.
- **A whole record that cannot be edited** is not a form of read-only
  fields: show it as a [Description List](?path=/docs/patterns-application-ui-description-list--docs),
  label and value with no box.

### Disabled

Disable a control only while it does not apply yet, and people can change
that on the same screen: a choice earlier in the form, a step not done.
Say what turns it on, in `helperText` or in the control that does it.

<DoDont
  do={<Story of={FieldStories.DoDisableWithReason} />}
  doCaption="Disabled for now, and the helper text says what turns it on."
  dont={<Story of={FieldStories.DontDisableWithoutReason} />}
  dontCaption="Nothing says why it is off or how to turn it on."
/>

- **Disable for "not yet", hide for "not you", read-only for "not
  changeable here".** An action or a field people's role never lets them
  use, and that they do not need to read, is left out, not shown disabled:
  a control they can never turn on is noise and a support ticket. A value
  they need to see but may not change is read-only.
- **No tooltip for the reason.** A disabled control leaves the tab order,
  so a tooltip on it never opens by keyboard or on touch. Put the reason
  in text people can see; `labelInfo` stays active on a disabled Field.
- **Dimmed on purpose.** Disabled controls are exempt from contrast
  rules and drop below readable contrast, one more reason not to disable
  a value people need to read.
- **Fields that turn off together** go in a disabled
  [`FormFieldGroup`](?path=/docs/patterns-application-ui-form-layouts--docs#field-groups):
  every control inside is disabled and dimmed, Checkbox, Switch and Radio
  included, and none is submitted. Slider and File Uploader do not read
  the group: give them `disabled` too.

## When not to use

- **Round a Zweihänder control.** Text Input, Textarea, Number Input,
  Select, Combobox, Date Picker, Checkbox, Switch and Radio have their own
  label, helper text and validation; a Field round one gives it two labels.
- **For a group of controls** under one name, use a
  [`FormFieldGroup`](?path=/docs/patterns-application-ui-form-layouts--docs#field-groups)
  (a `<fieldset>` and `<legend>`), or Radio's own group.

## Accessibility

- The label is a real `<label>` for the control: it is the control's
  accessible name, and clicking it focuses the control.
- `helperText` is the control's description (`aria-describedby`), read
  after its name.
- A read-only control keeps its place in the tab order and has the
  `readonly` attribute, so screen readers announce it as read-only;
  typing does not change the value, and the reason in `helperText` is read
  as its description.
- A disabled control is left out of the tab order; its helper text is still its description, so a screen reader browsing to it
  hears why.
- `validationState="error"` sets `aria-invalid="true"` on the control.
  Colour is never the only signal: the helper text says what is wrong.
- The required asterisk is `aria-hidden`; put `required` on the control so
  screen readers announce it.
- The info button is named by `infoLabel` ("More information") and
  described by the label, so a list of buttons tells which field each is
  for. It sits outside the `<label>`: pressing it opens the note without
  focusing the control. Enter or a press opens the note, a dialog named by
  the label; Escape closes it and returns focus to the button.
