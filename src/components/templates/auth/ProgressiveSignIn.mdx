# Progressive Sign In

A sign-in page that asks for the email first and only then decides how
the account signs in: accounts whose organization uses single sign-on go
to their identity provider, the rest are asked for a password. After
Carbon's login pattern. Built on the **Auth Layout** (see
[Sign In](?path=/docs/templates-auth-sign-in--docs#auth-layout)), its
`PasswordInput` and `AuthProviders`, and the kit's TextInput, Checkbox,
Spinner, Link, Alert and Button.

Use it when some of your customers sign in through their company's
identity provider (Okta, Entra ID, Google Workspace): they never see a
password field they cannot use. Where everyone signs in with a password,
use **Sign In**, which asks for both at once.

```sh
npx shadcn@latest add https://ontheshore.biz/zweihander/r/progressive-sign-in-template.json
```

## What works

- **Step 1, the email**: one field, **Remember my email** and Continue. An
  empty or malformed email is marked with a message and keeps focus. The
  email, trimmed, goes to `onContinue`, which returns the route.
- **The route is yours**: `onContinue` looks the account up (by the
  domain, say) and returns nothing for a password, `{ sso: 'Okta' }` for
  single sign-on, or a message such as "This account is locked".
- **Step 2, a password**: "Signing in as …" with **Change**, the password
  with Show / Hide, Forgot password? and Sign in. Focus moves to the
  password. The email is also in a hidden field, so a password manager
  fills and saves the right account. `onSignIn` gets the email, Remember
  my email and the password.
- **Step 2, single sign-on**: the title says where the reader is going,
  with a spinner and the email, while your redirect loads. **Use a
  different email** goes back; it cannot stop a redirect that is already
  loading, so it is for when the provider does not answer.
- **Change** and **Use a different email** go back to step 1 with the email
  filled in and focused.
- **Remember my email**: the template does not store anything. Store the
  email when `rememberEmail` is true and pass it back as `defaultEmail`;
  the field then starts filled in and the box ticked.
- **Social buttons**: `providers` puts them above the email on step 1, as
  on Sign In. They are for consumer identities (Google, Microsoft), not a
  company's single sign-on, which the email routes to.
- **When it fails**: `onContinue` and `onSignIn` return (or resolve to) a
  message. It shows above the form and is announced; a wrong password is
  cleared and focused. If they throw or reject, the page says "Something
  went wrong. Try again."

## Make it yours

`onContinue` calls your API with the email, which answers with the
account's sign-in method; for single sign-on, start the redirect (to
your identity provider's authorize URL) and return `{ sso }` with its
name for the page to show. Answer the same for an email with no account
as for one with a password, so the page cannot be used to find out who
has an account: the wrong password message then covers both. After
`onSignIn` succeeds, navigate on, or show a second factor.

## Props

| Prop | Values | Default | |
| --- | --- | --- | --- |
| `onContinue` | `(values) => string \| void \| { sso } \| Promise<…>` | | Gets `{ email, rememberEmail }`. Nothing: the password step. `{ sso: name }`: the single sign-on step. A string: a message above the form. |
| `onSignIn` | `(values) => string \| void \| Promise<…>` | | Gets `{ email, rememberEmail, password }`. A returned message shows above the form. |
| `defaultEmail` | `string` | | A remembered email: fills the field and ticks Remember my email. |
| `hasRememberEmail` | `boolean` | `true` | Shows Remember my email. |
| `providers` | `{ id, label, icon? }[]` | `[]` | Social buttons above the email, with an "or" line. |
| `onProviderSelect` | `(id) => void` | | Called with the button's `id`. |
| `title` | `ReactNode` | `"Sign in to your account"` | The `h1` of the email and password steps. |
| `forgotPasswordHref` | `string` | `"#forgot-password"` | On the password step. |
| `signUpHref` | `string` | | Shows "No account? Sign up". Leave it out where accounts are by invitation. |
| `footer` | `ReactNode` | | Under the form, outside the card. |

Every other Auth Layout prop passes through.

## Accessibility

- The form is in a `main` landmark, and its one heading is the `h1`.
- Continue replaces the email with the next step, so focus moves on: to
  the password, or to the new `h1` on the single sign-on step, where the
  spinner's "Taking you to …" is a `status`. Change and Use a different
  email put focus back in the email field.
- Change is named "Change email".
- An invalid field has `aria-invalid="true"` and its message as its
  description, and gets focus.
- The message from `onContinue` or `onSignIn` is an `alert`, and the button
  is `aria-busy` while it waits.
- The email for password managers is a `hidden` input: out of the tab order
  and the accessibility tree.
