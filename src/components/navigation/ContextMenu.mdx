# Context Menu

<DocTabs>
<DocTab value="overview">

A menu that opens at the pointer when someone right-clicks, or long-presses
on touch, an area: a table row, a card, an object on a canvas. Its items
are an action menu's, so it is a faster way to the same actions.

<Status of={ContextMenuStories} />

<Canvas of={ContextMenuStories.Default} />

## Variants

Context Menu has one look: the popup is a
[Menu](?path=/docs/components-navigation-menu--docs) popup and takes the
same entries: actions with icons and shortcuts, links, submenus, checkbox
and radio items, groups and separators.

| Area | Use for |
| --- | --- |
| Enabled (the default) | An area with actions on it. Right click and long press open the menu. |
| Disabled (`disabled`) | An area with nothing to act on right now. The browser's own menu shows instead. |

On a list or table, give each row its own Context Menu, with the same items
as the row's visible "more" button:

<Canvas of={ContextMenuStories.OnRows} />

## Measurements

The popup is Menu's, with the same items of the md control tier. It opens
with its top-left corner on the pointer, as the operating system's menus
do. Near the bottom of the window it flips above the pointer; near the
right edge it slides left to stay on screen. On
touch it opens at the finger after a 500ms press.

`items` is Menu's `items`. `children` is one element: the area itself, its
props and the open marker merged onto it, so a `<tr>` stays a row of the
table.

### Differences from the spec

- **No placement props.** Menu's `side` and `align` are left out: a context
  menu opens at the pointer, and flips on its own near the window edge.
- **Always modal.** There is no `isModal`: Base UI makes a context menu
  modal, as the operating system's menus are, so page scroll is locked
  until it closes.

## When to use

Use a Context Menu where people act on many things in place, rows of a
table, files, cards on a board, objects on a canvas, and expect the right
click they know from desktop apps. Put the same actions behind a visible
control too, a row's "more" button or a toolbar: the right click is a
shortcut, not the way in.

<DoDont
  do={<Story of={ContextMenuStories.DoShortcutToVisible} />}
  doCaption="The right click repeats the row's visible actions menu."
  dont={<Story of={ContextMenuStories.DontOnlyWay} />}
  dontCaption="Actions only a right click reaches. Nothing on screen says they exist, and keyboard and touch users may never find them."
/>

## When not to use

- **For the only way to an action.** Use a
  [Menu](?path=/docs/components-navigation-menu--docs) from a visible
  button, or Buttons; add a Context Menu with the same items on top.
- **On text people read or copy.** A right click there should keep the
  browser's menu: copy, look up, translate.
- **For a tool's commands by category.** Use a
  [Menubar](?path=/docs/components-navigation-menubar--docs).

## Accessibility

- A right click on the area opens the menu at the pointer and outlines the
  area while it is open.
- The popup is Menu's: `role="menu"` with `menuitem` entries, and the keys
  inside are Menu's: the arrows move, Enter runs the action and closes.
- Shift+F10 or the Menu key open it from the keyboard: the browser fires
  `contextmenu` on the focused element, so the area, or a control in it,
  must take focus.
- Escape closes it and returns focus to where it was.
- Nothing announces that a context menu exists, so each of its items must
  also sit behind a visible control, such as the row's "more" button,
  named after the row.
- `disabled` leaves the browser's own menu in place.
- It is modal: page scroll is locked while it is open, so the menu is the
  only thing to interact with.
