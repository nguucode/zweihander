# Components

Single, reusable UI components (atomic design's "molecules"). Reference list: [uiguideline.com/components](https://www.uiguideline.com/components).

Each component lives in `src/components/<category>/`, with its story set to
`Components/<Category>/<Component>`. Categories below — add a component to the
one it fits, or propose a new category if none fit.

| Category | Components |
| --- | --- |
| **Atomic Elements** | Divider ✅, Badge ✅, Avatar ✅, Tag ✅, Kbd ✅ |
| **Buttons** | Button ✅, Toggle Button ✅ |
| **Controls** | Color Picker ✅, Rating ✅, Slider ✅, Switch ✅, Checkbox ✅, Radio ✅ |
| **Data Display** | Calendar ✅, Table ✅, Accordion ✅, Carousel ✅, Card ✅, Collapse ✅ |
| **Inputs** | Field ✅, Search ✅, Number Input ✅, Text Input ✅, Password Input ✅, Textarea ✅, File Uploader ✅, Date Picker ✅, Select ✅, Combobox ✅ |
| **Loaders** | Spinner ✅, Progress Bar ✅, Skeleton ✅ |

## How a component page reads

Every component page has the same three tabs, after Material 3, so the
answer you need is always in the same place.

| Tab | Answers | What is on it |
| --- | --- | --- |
| **Overview** | What is it? | One-line description, the main example, a gallery of variants with when to use each, the status, and Resources: the import line, the registry command, the source. |
| **Specs** | How is it built? | Anatomy (the real component with numbered parts), Measurements for every size, Color for every variant, States side by side, and the API table with live controls. Where Zweihänder departs from the reference spec, "Differences from the spec" says how. |
| **Guidelines** | How do I use it well? | When to use it, when to reach for something else, Do and Don't pairs rendered from real stories, and Accessibility: keyboard, roles and states, each line checked by a test. |

Every value on Specs is read live from the tokens, so it follows the theme
in the toolbar and cannot drift from the code. `npm run docs:check` fails CI
when a component page is missing a tab or a required section.

## Behaviour comes from Base UI

Components are styled with CSS Modules over the token layer; their
*behaviour* — focus, keyboard, ARIA — comes from
[Base UI](https://base-ui.com) (`@base-ui/react`) wherever it is more than
trivial. Button uses its `Button` for the focusable-while-loading state;
Toggle Button, the form controls, the overlays, Select, Combobox, Tabs and
Menu are built on its parts.

The reason is the same one that kept this kit from hand-rolling them: a
Modal needs a focus trap, scroll locking, an inert background and correct
restore-focus; Select and Combobox need typeahead, virtual focus and a
listbox ARIA contract; Menu and Tabs need roving tabindex. Those are not
lines of code, they are years of accumulated edge cases in screen readers
and browsers. Base UI is unstyled, so it carries none of that into the
look — the tokens still decide everything you can see.

Two conventions follow from it:

- **`render` instead of `asChild`.** Any component that renders an element
  you might want to replace takes a `render` prop — an element or a
  function — the same as Base UI's own parts and shadcn's.
- **Base UI's change handlers.** Components built on it expose its names:
  `onPressedChange`, `onCheckedChange`, `onValueChange`, `onOpenChange`.
  Components that wrap a real `<input>` (Text Input, Textarea, Search)
  keep the native `onChange(event)`.

Components with no behaviour worth the name — Divider, Badge, Avatar,
Tag, Kbd — are plain elements and do not import it.
